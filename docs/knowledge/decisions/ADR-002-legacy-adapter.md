# Context
Home Assistant drives the L513 through hand-written YAML on `unipi1/…` and `unipi/<area>/…`
topics. Matthijs asked for an adapter "that runs the old logic in a separate script file, so
we can easily disable it with a single setting", and to check which functions must move to
the main script or to HA + generic options.

# Decision
1. A separate module `legacy_adapter.py` next to `hass-unipi.py`.
2. Single switch: `config.json` → `"legacy": {"enabled": true|false, ...}`. When `false`
   the module is **not imported**, no legacy topic is subscribed or published.
3. The adapter is **translation-only**: it subscribes to legacy command topics and calls the
   core `CommandService`; it listens to the core `EventBus` and publishes legacy state
   topics/payloads. It contains **no timers that drive hardware, no evok access, no rules**.
4. Every old *behaviour* (doorbell sequence, duration, PIR hold, NC logic, counter, lux
   scaling, sensor averaging, local bel/dimmer/switch) is implemented in the core as a
   generic per-circuit option (see `/analysis/feature-gap-matrix.md`), and configured for
   the L513 by the converter (T22).
5. Old local handling (`handle_local`) is **converted to core local rules**, never executed
   by the adapter — otherwise disabling the adapter would silently break wall switches, and
   running both would ring the bell twice.

# Consequences
- Disabling the adapter changes *topics only*; functions remain → safe incremental HA
  migration (T40) and trivial removal (T42: delete file + config key + map file).
- Adapter state is limited to translation bookkeeping (e.g. last counter value for
  `counter_delta`, last AO level for legacy `on` without brightness).
- Adapter needs a map file `legacy_map.json` (legacy topic ↔ core `dev/circuit`, payload
  style), generated by T22 from the old config + T31 circuit map, then human-verified.
- The core must expose a small internal API (`EventBus`, `CommandService`) — T10. This also
  makes the core easier to test.
